# 履约监控与故障验收

多仓履约可以作为 Java 后端面试主项目。建议围绕两条调用链展开：旧 ERP 和履约命令如何共用库存并发约束，以及业务事务已经提交、消息投递失败后如何恢复。两条链路分别有数据库不变量和真实依赖故障验收可追问。

| 原有缺口 | 本次补充 | 证据范围 |
| --- | --- | --- |
| 排障依赖手查数据库 | 采样 Outbox、Inbox、文件任务的状态计数与最老积压 | Actuator 暴露 Prometheus 指标，按业务状态观察 |
| 验收命令分散 | 独立库恢复脚本和 GitHub Actions 工作流 | Java 17 构建、履约单测、真实 MySQL/Redis/RabbitMQ 的故障验收 |
| 性能数字容易被误读 | 保留 M7 的合成数据和同机实验条件 | 可讲索引和热点锁的因果关系。生产 SLO、混合长压与依赖高可用需要独立验证 |

## 从故障场景理解代码

1. ERP 入库 6 件，销售单绑定履约后申请预占 4 件。申请成功时物理库存 H=6，预占 R=4，预占记录及流水增量也是 4。绑定和分配的两条事件随各自业务事务持久化。
2. 让应用连接一个不监听的 TCP 端口。RabbitMQ 发布失败，Outbox 进入 `RETRY_WAIT`，Inbox 没有处理记录。指标能同时反映积压数量和最老等待时间。
3. 重启应用并指向可用 RabbitMQ。发布确认后 Outbox 记为 `SENT`，消费者提交后 Inbox 记为 `PROCESSED`，读模型追上最新事件版本。重用原预占幂等键，返回同一份结果，事件总数和库存不变量保持原值。

Broker 确认回答的是消息是否被 Broker 接受。Inbox 处理状态回答的是消费侧事务是否完成。这个区别决定了排障时先看哪个积压，也解释了为什么应用要在消费侧做幂等。

## 开启指标

在已初始化的本地环境重启后端时，使用 `./scripts/Start-Local.ps1 -Observability`。直接运行 jar 时，激活 `fulfillment,fulfillment-observability`。从运行应用的同一台机器访问 `http://127.0.0.1:48085/actuator/prometheus`，可用 `FULFILLMENT_MANAGEMENT_PORT` 改端口。

| 指标 | 排障用途 |
| --- | --- |
| `fulfillment_queue_records{queue,status}` | 区分投递重试、消费重试、死信和文件失败。文件 `PARTIAL_FAILED` 表示有部分行失败，具体结果查任务详情 |
| `fulfillment_queue_oldest_pending_seconds{queue}` | 判断最老未完成记录等了多久。终态从年龄计算中排除 |
| `fulfillment_queue_sample_success` | 最近一次采样是否成功 |
| `fulfillment_queue_sample_last_success_timestamp_seconds` | 用 `time() - fulfillment_queue_sample_last_success_timestamp_seconds` 判断快照新鲜度 |

采样默认每轮结束后等 15 秒，三个查询各有 3 秒查询超时。查询走独立调度线程，指标抓取读取内存快照。启动首次成功采样前，队列值为 `NaN`。采样失败会保留最近有效数据，并把成功标志置零。三个表顺序查询，跨表数值可能有时差。指标是按共享数据库聚合的全局值，同库多个应用实例的读数不能相加。积压和死信增长会增加采样读开销。管理端口只监听回环地址，外部采集方案需单独配置认证与访问范围。

## 复现与证据

在 `项目代码/backend` 构建并运行履约测试。

```sh
mvn -B -ntp -pl yudao-server -am package "-Dtest=cn.iocoder.yudao.module.fulfillment.**.*Test" -Dsurefire.failIfNoSpecifiedTests=false
```

在 `项目代码` 安装 `tests/requirements.txt`。准备独立的 MySQL、Redis 与 RabbitMQ，并配置 `CI_MYSQL_USER`、`CI_MYSQL_PASSWORD`、`CI_MQ_USER`、`CI_MQ_PASSWORD`、`CI_MQ_VHOST`。MySQL 用户需能创建并操作 `fulfillment_ci_*` 新库，客户端程序可用 `CI_MYSQL_CLIENT` 指定。脚本会保留新库便于查验，停止它启动的两个 JVM。每个并行运行需要各自的 Redis 实例或 DB、RabbitMQ vhost 和应用端口。

```sh
python tests/fulfillment_recovery_smoke.py --mysql-port 33316 --redis-port 36389 --mq-port 35692 --output .local/ci/fulfillment-recovery.json
```

2026-11-14 本机通过 60 项履约单测及 18 项真实依赖验收。测试在新建 MySQL 库、独立 Redis 和 RabbitMQ 下完成。故障期间实测两条事件进入待重试，恢复后两条事件全部发送并处理，原预占命令重放后 H=6、R=4。
