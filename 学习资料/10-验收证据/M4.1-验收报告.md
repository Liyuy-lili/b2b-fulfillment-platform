# M4.1 验收报告：自动到期释放

日期：2026-10-19（Asia/Shanghai）。范围仅 M4.1；M4.2退货与M4.3核对尚未实施，不代表整个M4完成。

## 1. 本部分新增内容

| 位置 | 实际改动 |
| --- | --- |
| `FulExpiryScanner`、调度配置和参数 | Spring独立单线程定时器；全局无锁候选、按期限/ID游标分页、每轮有界、到尾回绕、异常行后续重试 |
| `FulExpiryService` | 每候选一笔RC事务；命令→源单→主/明细→预占→库存；等完锁再检查当前时间与held |
| `FulCommandService` | Java内部EXPIRE系统命令，actor0，tenant+actor+type+key持久化幂等；无HTTP新接口或客户端绕过参数 |
| `FulAllocationService` | 持久化和预占流水辅助方法允许显式系统actor；原HTTP入口仍从当前登录用户取actor |
| 租户与审计 | 候选租户有效性验证；TenantUtils finally恢复上下文；系统审计actor0 |
| 库存效果 | 仅剩余held/R/reserved→released/open，H与ERP实物流水不变；更新派生状态和版本 |
| 故障profile | 专用 `fulfillment-expiry-fault-test` 在全部业务写入后、命令完成前抛错；主profile不加载 |
| M3回归脚本 | 默认适配自动释放；`M3_EXPECT_AUTO_EXPIRY=0`仅用于旧M3二进制复现，支持新证据文件名避免覆盖历史 |

固定基座、许可证和ERP唯一实物写入来源保持。本部分没有新DDL，主库和新库历史仍为0/1/2/3；V1/V2/V3未修改。退货/核对需要的新表和V4将在后续部分实现。

### 实际关键场景

1. **自然60秒到期**：订购3.123456，H=5；发1.123456，手动释放0.111111；自然到期只释放剩余1.888889。最终H=3.876544、R=0、open=2、shipped=1.123456、cancelled=0；没有修改这条记录的截止时间。
2. **同一候选双实例**：锁住源单让两个JVM都读到候选；两个实例日志都观察到相同EXPIRE结果，SQL仅一条到期流水、一条系统命令。日志重放不等于再次释放。
3. **全部写入后失败**：专用profile实际抛错且再次重试；余额、订单/预占数量及版本保持原值，EXPIRE流水与命令均回滚。停止故障实例，启动正常实例后同一系统键成功完成。
4. **失败首行与后页**：配置每批2条/每轮1批，第一条源单锁超时，真实进入整事务有界重试；后面6条仍在首行解锁前完成，随后回绕处理首行。
5. **发货等待跨期限**：发货先取订单/预占锁，等库存锁时跨过期限；释放外部库存锁后，发货明确返回1080000020，没有ERP出库、H不变；随后正常到期释放。
6. **合法先发完**：期限前完成发货，随后扫描不把consumed重新释放，订单保持FULFILLED。
7. **取消/手动释放竞争**：与到期处理串行化后只产生合法数量结果，无负数或重复释放；取消仍转cancelled，自动到期转open。
8. **多租户**：真实创建第二租户并交错处理两个租户的预占，系统命令各自tenant、actor0正确；原跨租户HTTP读取仍被拒绝。单测覆盖成功/异常后的上下文恢复与无效租户跳过。
9. **新JVM补扫**：停止两个工作进程后让持久化预占到期，新进程从初始游标恢复完成；重复扫描没有第二条业务效果。
10. **重新分配**：到期后open可重新预占，产生新reservation ID；原发货命令仍能重放，历史EXPIRE不影响新预占。

为安排锁竞争和积压，测试只对有标签的fixture截止时间执行SQL注入，全部记录在 `deadline_injections`；H/R和业务数量均由HTTP/真实业务服务写入。不能把这些注入场景称为全部自然等待到期。

## 3. 主库行为与运行环境

主库首次启用扫描器，实际释放129条历史已到期预占。逐预占、库存行和订单项核对证明：H和ERP实物流水保持、reserved减少等于held释放、open等量增加、shipped/cancelled/returned不变；每笔系统效果对应一条actor0流水。旧订单可能由RESERVED变为WAIT_STOCK，这是本次业务规则的实际效果。

主服务继续使用15173/48080/33306/36379。独立验收库为 `fulfillment_m4_expiry_20261019_004816`，测试端口48082/48083与Redis DB4；脚本退出停止自己创建的进程，保留库和测试数据。M3回归另用主库/Redis DB0。系统MySQL80的3306未改。

本机profile默认启用，参数位于 `application-fulfillment.yaml`：每批50、最多4批、轮间5秒。设置 `FULFILLMENT_EXPIRY_ENABLED=false` 并重启可停扫描；发货自己的期限校验仍然有效。没有启用Quartz、引入MQ或改变事务传播。调度间隔不是实时SLA，停机后的补扫速度也没有压测承诺。

## 4. 复现命令

```powershell
# 后端：在backend目录
./mvnw.cmd -B -ntp -pl yudao-server -am package '-Dtest=OrderStatusCalculatorTest,AllocationPlannerTest,DatabaseCommandRetryTest,LogisticsSignatureTest,FulExpiryScannerTest' '-Dsurefire.failIfNoSpecifiedTests=false'

# 独立验收：在项目根目录。每次默认创建新的项目专用库，既有库不会被重建。
$env:M0_PWSH=(Get-Process -Id $PID).Path
C:/veighna_studio/python.exe tests/m4_expiry_acceptance.py

# 主库启用和完整重启：暂停其他写入后执行，会重启本项目前后端与依赖。
C:/veighna_studio/python.exe tests/m4_expiry_main.py

# M3当前回归；默认按自动到期校验，保留原M3证据
$env:M3_EVIDENCE='M4.1-M3-regression.json'
$env:M3_INSTANCES_EVIDENCE='M4.1-M3-instances.json'
$env:M3_EXPECT_AUTO_EXPIRY='1'
./tests/m3_instances.ps1 -TestFiles m3_acceptance.py
```

`m4_expiry_main.py`首次启用计数随当前事实改变，重新执行时可能没有新增到期流水；不能复用129这个数作为下次预期。所有历史执行日志和报告只描述当次实际状态。

## 5. 范围与剩余风险

- 退货、核对报告、Outbox/RabbitMQ、异步文件任务、仓库细粒度授权、压测尚未实施。没有自动更正库存事实，也没有到期积压看板或告警。
- 实验为同机多JVM，截止时间和发货检查用应用UTC时钟；没有验证跨机时钟偏差，跨机部署需时间同步。
- 无效租户保留到期预占，恢复有效后补扫；持续数据错误记录日志并重试，需后续核对/人工处理。任务记录数有界，每条可能等待锁，所以单轮耗时不作保证。
- 未重跑全部八类旧库存入口、全部上游单测、全仓前端检查、Docker或压测。本轮未修改ERP实物库存写入代码或前端；M3历史回归证据保持原文。
- 正常完整重启不等于突然断电；本轮故障实验为事务内抛错及工作进程停止后补扫，没有声称测试全部操作系统崩溃窗口。
- 没有创建本地Git提交、推送或PR；源文件仍在当前工作区。不修改Codex用户记忆。
