# M2 验收报告：预占、释放与统一库存保护

日期：2026-10-18。M2 已完成，构建、迁移、业务验收、回归、从零安装和完整依赖重启门禁均已通过。

## 1. 交付范围

- 新增 `allocate`、`release`、订单预占记录和单行 H/R/A 查询。
- 分配/释放只改变 R、预占、履约数量和预占流水，实物 H 仍由 ERP 唯一写入。
- 实现 PRIORITY_SPLIT、SINGLE_FIRST 与稳定回退；本次全部 open 满足才增加预占。
- 绑定、分配、释放共享持久化命令记录；按 tenant/actor/type/key 隔离与摘要校验。
- 新增最外层有限重试，旧 ERP 事务入口也接入；最多三次，锁失败才重试，加入外层事务时向外传播。
- 八类库存入口批量锁库存、当前读、检查 H≥R、精确记录余额；库存 SUM 去掉 double 转换。
- 基本单位创建后不可修改；库存生效时拒绝非正自然数量或不一致盘点差额。
- V2 增量迁移，保留 M0 SQL 与已执行 V1；前置检查脏库存，增加 R 与数量/关联/active 约束及权限。

完整流程讲解见 [M2 学习文档](../03-阶段原理讲解/M2-预占释放与统一库存保护.md)，兼容决策见 [ADR-011](../05-设计决策与复盘/ADR-011-M2-预占与统一库存写入.md)。

## 3. 并发和精度的具体证据

- 两个不同 PID 的 JVM，分别监听 48080/48082，共享 MySQL `fulfillment` 与 Redis DB0；不是两个线程假扮两个实例。
- 8 个订单每单要 3，共同争抢 10：恰好 3 单成功，R=9≤H=10。
- 同键并发跨两实例：6 请求返回同一响应，只产生一份预占和一条命令记录。
- 同键不同参数拒绝；仓库顺序、等值十进制表示规范化；不同 actor、不同 command type 独立。
- 一个 SKU 不足时整单没有部分 R；相同旧键保持原不足结果，补货后新键可以成功。
- 重复商品行共享余量；缺失行视为零；全释放后 held/active 归零，再分配正常。
- 两个首次入库并发，只形成一个库存身份，余额为精确的 0.000002。
- 直接 BigDecimal SUM 验证 `9007199254740992.000002`；预占验证 DECIMAL(24,6) 最大合法值 `999999999999999999.999999`。
- 测试真实持有库存行超过 3 秒，观察到服务端 next attempt=2；新命令及旧审核分别验证整事务重试与无重复效果。日志片段保存在各自 JSON 内。
- H、R、held 汇总、预占流水、实物流水逐行累计均核对。直接 SQL 的约束探针在回滚事务中验证 H<R、R<0、逻辑删除被 CHECK 拒绝。

## 4. 旧入口覆盖

调用清单及源文件哈希：[M2-stock-writers.json](M2-stock-writers.json)。

| 入口 | 主要减少路径 | 反向 / 其他验证 |
| --- | --- | --- |
| 其他出库 | 出库不能消耗 R | 合法出库正好消耗 A；反审核只增加 H |
| 销售出库 | 未托管源单出库受 A 约束 | 反审核增加 H；托管入口仍冻结 |
| 调拨 | 调出受 A 约束 | 反审核不能取走已被预占的调入量；双仓一起回滚 |
| 盘点 | 盘亏受 A 约束 | 盘盈撤销也受约束；盘亏撤销增加 H |
| 采购退货 | 退回供应商受 A 约束 | 反审核增加 H |
| 采购入库 | 增加 H | 反审核不能消耗预占 |
| 其他入库 | 增加 H | 反审核不能消耗预占 |
| 销售退货 | 收回增加 H | 反审核不能消耗预占 |

还验证了第二行失败会回滚第一行余额/流水、两实例反向调拨、新分配与旧出库竞争，以及八个入口的非法数量/差额输入。

自然数量校验位于库存生效边界，部分基座仍允许保存非法草稿。被拒绝的草稿保留在验收数据中，不自动清理，也不将其写成已经生效的库存事实。

## 5. 迁移、安装与恢复边界

- M0 81 表初始化文件保持；V1 哈希核对保持。新库显式 baseline 后按顺序迁移。
- `StockMigrationPreflight` 在 migrate 的 DDL 前检查重复身份、负 H、已删除库存，以及已有 R 的范围；发现问题列出 ID/租户/商品/仓库，中止，不自动合并。
- 独立坏库 `fulfillment_m2_dirty_20261018` 专供拒绝测试，最终保留两条重复身份记录，没有执行 V1/V2，不可当正常演示库使用。
- 独立新库 `fulfillment_m2_clean_20261018` 正常安装并运行，应用 48081、Redis DB2；验收结束停止自己的 Java 进程，不与主库混用缓存。
- V2 不能在应用仍使用旧二进制写库存时滚动混部。本地先停应用、迁移，再启动同一新产物；第二实例也是同一产物。没有宣称支持旧/新版本在线滚动升级。
- MySQL 多条 DDL 不构成整份迁移的单个可回滚事务。失败需检查实际 schema 和 Flyway 历史，修复后人工决策；没有自动 clean/repair/重置业务数据。
- Flyway 固定 BOM 仍提示 MySQL 8.4 高于其最高测试版本 8.1；实际迁移/启动/回归通过，不忽略兼容提示或擅自升级。

## 6. 怎样复现

```powershell
# 已完成初始化 / baseline 的本机
./scripts/Build.ps1
./scripts/Stop-Local.ps1
./scripts/Migrate-Database.ps1 -Action migrate
./scripts/Start-Local.ps1
# 脚本启动同库第二 JVM、执行测试，最后关闭自己的第二进程
./tests/m2_two_instance.ps1 -TestFiles m2_acceptance.py,m2_legacy_inventory.py,m2_permissions.py
```

上面 Build.ps1 仍按原参数跳过上游单测。本轮实际用于打包和指定领域测试的命令见构建摘要；指定测试为 `OrderStatusCalculatorTest,AllocationPlannerTest,DatabaseCommandRetryTest`，同时设置 `-Dsurefire.failIfNoSpecifiedTests=false`。

主回归脚本需顺序运行，避免其他业务写入干扰全库库存快照：`m1_acceptance.py` → `m1_locking.py` → `m0_smoke.py`。可通过 `M1_EVIDENCE`、`M1_LOCK_EVIDENCE`、`M0_EVIDENCE` 指定新的证据文件，保留历史验收。

完整重启门禁：先暂停写入并停止第二/独立验证实例，再运行 `python tests/m2_restart.py`；需要 PowerShell 7，必要时通过 `M0_PWSH` 指定。

`m2_migration.py` 为初次升级/坏库试验，不能直接在已经升级的库上重复首次迁移断言。日常运行 validate；独立新库运行参数与证据见安装结果及 `m1_clean_install.ps1` 的可选参数。

## 7. 本轮修正记录与限制

- 仓库 sort 实际是 Long，初版 Integer 映射编译失败；改为 long 全程排序后构建通过。
- 某些上游创建接口要求供应商/基本单位，即使 VO 标记看似可选；验收 fixture 按实际接口补齐。这些初版失败没有算作通过。
- Druid 的初版锁等待配置键未被实际类型接收；根据固定依赖代码更正，并在启动读取真实连接校验。重试测试增加日志断言，不把普通等待成功说成重试成功。
- 发现负自然数量会反向制造库存的风险，补充八入口生效校验后复验；不重写所有上游草稿规则。
- 旧 ERP 的源单/单据状态锁仍在库存之前，统一的是共享库存键的批量升序协议。M3 适配器接入还需审查新依赖，不能说全系统已无死锁。
- 逻辑删除由 CHECK 拒绝，应用没有库存行删除接口；管理员直接 SQL/硬删除不属于应用协议。仓库等主数据生命周期的完整并发协议仍需后续扩展。
- 当前权限为功能、租户、订单归属；细粒度仓库授权在 M6。当前预占记录查询按单列出历史，后续工作台需补历史分页。
- 手工释放支持过期持有量；自动扫描在 M4，发货与过期竞争在 M3/M4。测试预占可能到期但不会被本阶段后台自动释放。
- 无新增前端文件。M1 页面可显示新的数量/状态，正式分配/发货工作台属于 M3；未执行前端重构、全量类型清理、Docker 运行、MQ 或压测。
- 源码和许可证保留，仍无本地 Git 提交、推送或 PR。改造清单见 [M2-changes.json](M2-changes.json)。
