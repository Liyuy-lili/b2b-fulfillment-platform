# ADR-013：M4.1 到期扫描与系统命令

> 阅读语境：以下正文记录该阶段当时的实现和取舍，早期“后续待做”仅为历史状态。当前M0—M7已经完成，请结合[现行总目录](../README.md)与系统教程。工程验收原件未改。

日期：2026-10-19。状态：已实施并验收。范围仅 M4.1，退货和核对仍待后续部分；实际证据见 [M4.1验收报告](../10-验收证据/M4.1-验收报告.md)。

## 背景与决定

本机 profile 显式排除了 Quartz 自动配置，没有启用其任务表和执行器。使用 Spring `@Scheduled`、独立单线程 `ThreadPoolTaskScheduler` 扫描预占到期；这是对原规格“复用 infra 定时机制”的明确调整。固定基座、库存事实来源、事务边界与消息语义保持。

- 由 `fulfillment.expiry.enabled` 显式启用，本机 profile 默认启用，可通过环境变量关闭。默认每批50条、每轮最多4批、轮间5秒；参数有上下界。默认每轮最多处理200条，可在验证范围内调整；不保证5秒内完成，锁等待会延长一轮。
- 全局只读候选扫描使用既有 `(active_flag,expire_at,id)` 索引与 `(expire_at,id)` 游标，不持有预占锁。游标跨轮保留，扫到尾部回绕。异常行仍保留待扫描，进程重启从头扫描；游标不代表业务成功，也无需持久化。
- 每个候选进入自身租户上下文并验证租户有效，finally 恢复原上下文；禁用/过期租户暂不处理，重新启用后补扫。无用户登录模拟，系统命令与审计 actor 固定0。没有对外到期命令接口或管理员绕过参数。
- `EXPIRE` 幂等身份为 tenant+actor0+类型+reservation ID；与前台使用同一命令表。整事务位于重试器内部，显式 RC，最多3次数据库锁失败重试。失败回滚命令和全部业务事实，下轮再试。
- 锁依赖：命令→ERP源单→履约单→订单项→按ID预占→库存。持有全部必要锁后重查 held/期限。已关闭返回幂等无操作；未来期限候选抛内部异常回滚，不能持久化“尚未到期”而永久阻止后续到期。
- 只将当前剩余 held 从 R/reserved 转回 open，写 EXPIRE 预占流水，H和ERP实物流水不变；已发货/已释放/已取消部分不重复处理。更新订单派生状态和版本。
- 专用故障 profile 在写完预占、余额、订单和流水后、完成命令前抛错；主 profile 不加载它，没有HTTP故障开关。
- 本部分没有新DDL，V1/V2/V3保持原文，不为阶段编号而创建空V4；退货/核对启用时再设计V4。

## 验证要求与边界

验证自然到期、双JVM重复扫描、发货等锁跨过期限、取消/释放竞争、局部发货后只释放剩余量、故障回滚恢复、失败首行不阻塞后续页面、租户上下文恢复和重启补扫。记录实际证据，不把轮间隔当实时SLA或吞吐指标。

到期正确性由发货命令当前读重新检查期限与数据库锁保证。调度器晚到不允许过期发货；定时任务不是分布式锁。大量积压、租户失效和持续数据错误仍需看日志并人工处理，核对报告属于M4.3。本阶段不引入MQ、租约或自动事实修复。
