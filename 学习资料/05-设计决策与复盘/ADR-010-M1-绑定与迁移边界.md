# ADR-010：M1 绑定与迁移边界

> 阅读语境：以下正文记录该阶段当时的实现和取舍，早期“后续待做”仅为历史状态。当前M0—M7已经完成，请结合[现行总目录](../README.md)与系统教程。工程验收原件未改。

日期：2026-10-17。状态：已实施并验收，证据见 [M1 报告](../10-验收证据/M1-验收报告.md)。

- 保持固定基座、同库事务及 ERP 实物库存唯一来源。M1 不改库存数量。
- Flyway 使用 Boot BOM 管理的 11.7.2，专用历史表 `ful_flyway_schema_history`。先验证 M0 的 81 张表及字段，再通过独立命令显式 baseline 0；启动只能 migrate/validate，禁止自动 baseline 与 clean。
- Flyway 启动迁移使用配置中同一数据库凭据的短生命周期 JDBC 连接，业务仍使用原 Druid 池。实测 Flyway 可选权限探测触发 Druid 丢弃连接，后续读取失败；使用独立迁移连接避免为探测扩大数据库权限。
- 保留 BOM 固定 Flyway 版本；它对 MySQL 8.4 提示其最高测试版本 8.1。本机迁移/启动/校验已通过，兼容提示保留在验收风险记录，不自动升级固定依赖。
- V1 建立九张 P0 表及菜单；M1 仅启用订单、订单项及绑定命令记录，其余表为 M2/M3 的持久化基础。库存预占列在 M2 增加。
- 绑定使用 READ_COMMITTED、先锁 ERP 源单，再检查托管记录及任何出库/退货记录（包括逻辑删除的历史）。初始数量全部为 open，保存商品、单位、价格、税率及商业字段快照。
- 本项目 profile 的业务数据源默认统一 READ_COMMITTED（JDBC 2），启动读取真实连接并校验。受控并发试验发现 RR 下“旧源单无托管记录”的锁定读会持有间隙锁，可能阻塞另一源单的绑定插入，和源单行锁形成死锁。RC 避免该缺失记录查询保留间隙锁；仍保留源单锁与托管当前读，不宣称所有死锁因此消失。事务仍覆盖原有整条 ERP 业务操作，未拆分提交；其他上游 profile 不修改。
- ERP 定义托管策略接口与源单锁守卫；履约模块提供实现，ERP 不依赖履约。所有销售单与关联出库/退货修改按源单 ID 升序取得锁；关联单据若等待期间被改挂其他订单，拒绝本次写入。
- M1 尚无内部履约出库端口，所以绑定后拒绝所有旧手工出库/退货写入，不提供请求参数或 ThreadLocal 绕过方式。M3 再增加明确的内部适配端口。
- 绑定已是写命令，因此在 M1 实现其幂等记录（M2 扩展复用）；范围 tenant+actor+command+key，保存请求摘要和原始返回 ID。重复返回前仍验证当前权限与对象范围。
- M1 数据范围：当前租户的超级管理员 / 租户管理员可操作租户内全部，其余操作者仅能绑定、读取自己创建的销售订单对应履约单。部门/仓库粒度由 M6 扩展。
- 新接口只返回字符串 ID 和十进制数量字符串；新记录审计时间按 UTC 写入，新增 API 返回 ISO-8601 时区时间；上游 DTO 保持原约定。
- 绑定快照及命令记录可追溯绑定事实；可靠 ORDER_BOUND 事件在 M5 接入 Outbox 后实现，M1 不声称可靠消息已存在。

验收：数量状态单测；真实 MySQL 显式迁移、新库与旧基座库、校验失败；重复/并发绑定、旧入口冻结、跨租户和非管理员数据范围；M0 回归。
