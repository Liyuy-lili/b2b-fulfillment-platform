> 阅读语境：以下正文记录该阶段当时的实现和取舍，早期“后续待做”仅为历史状态。当前M0—M7已经完成，请结合[现行总目录](../README.md)与系统教程。工程验收原件未改。

日期：2026-10-18。设计边界见 [ADR-011](../05-设计决策与复盘/ADR-011-M2-预占与统一库存写入.md)，运行结果见 [M2 验收报告](../10-验收证据/M2-验收报告.md)。

## 1. 用一笔订单理解 H、R、A

客户要买 7.000001 件商品，两仓分别有 3.123456、6.000001 件。

| 时点 | 仓 A 的 H / R / A | 仓 B 的 H / R / A | 订单 |
| --- | --- | --- | --- |
| 分配前 | 3.123456 / 0 / 3.123456 | 6.000001 / 0 / 6.000001 | open=7.000001 |
| 按优先级预占 | 3.123456 / 3.123456 / 0 | 6.000001 / 3.876545 / 2.123456 | reserved=7.000001 |
| 从 A 释放 1.123456 | 3.123456 / 2 / 1.123456 | 保持 | open=1.123456，reserved=5.876545 |
| 重新分配待分配量 | 恢复全占 | 保持 | reserved=7.000001 |

- **H**：ERP 实物库存，仓库真正有多少。
- **R**：已经承诺给订单但还没发出的数量。
- **A=H−R**：其他订单和旧 ERP 出库还能使用多少。

预占和释放都不改变 H。没有发货，也不生成 ERP 实物出库流水。M3 才会通过 ERP 适配器完成唯一一次实物扣减。

## 3. 正式分配怎样执行

核心入口：`FulAllocationController.allocate` → 外层 `DatabaseCommandRetry` → 事务代理 → `FulAllocationService.allocate`。

```text
命令记录：tenant+actor+ALLOCATE+key
  → 请求摘要比较
  → 锁 ERP 源单
  → 锁履约单、检查当前权限与归属
  → 已成功处理则返回保存的响应
  → 锁履约项
  → 校验本租户启用仓库、商品基本单位
  → 按 product/warehouse 升序锁候选库存
  → 基于最新 H/R 运行纯计算策略
  → 足够：更新全部 R、插入预占与流水、open 转 reserved
  → 不足：不增加任何 R，仅保存等待状态与命令结果
  → 整体提交
```

数据库锁的顺序与仓库业务优先级不是一回事。锁按商品/仓库 ID 排序，避免两请求反向拿锁；拿齐锁以后，策略才按仓库 sort/id 决定从哪里预占。

缺失库存行视为零。预占不靠“锁不存在的行”承诺将来的库存；不足时不会为了分配而生成库存行。

## 4. 为什么一个商品不足，就整单不增加预占

例如订单需要 A 商品 5 件、B 商品 3 件，仓库有 A=10、B=2。

首版规则是本次所有 open 都满足才分配。计划计算完之前不写 R；看到 B 不足，返回 `INSUFFICIENT_STOCK`，订单进入等待，但 A 的 5 件不会被悄悄占住。

这是一次正常业务结果，使用成功响应中的 outcome 表达。若相同幂等键重发，应返回原来的“不足”结果。补货后重新发起分配属于新的业务尝试，应使用新键。

数据库错误、权限错误、非法数量会回滚；“库存不足”则允许保存此次尝试与等待状态。面试时需要分清这两种情况。

## 5. 两种策略到底差在哪里

### PRIORITY_SPLIT

仓库按 sort、ID 排序。每个商品逐仓分配，直到满足需求。

### SINGLE_FIRST

先找一个能满足整张订单全部商品的仓库；找不到才回退优先级拆仓。不是分别给每个商品挑一个仓，也没有使用不存在的地理距离数据。

同一商品在订单中出现两行时，两行必须共享剩余库存。仓库只有 5 件，两行各要 4 件，不能各自读到 5 并承诺总共 8。`AllocationPlanner` 用按商品/仓库标识的剩余量完成纯计算。

不同商品的数量不合并成“总件数”。SKU 的基本单位创建后不可修改；需要换单位时建立新 SKU，首版不做单位换算。

## 6. 释放与取消的区别

释放表示把承诺还回去，让订单重新等待分配：

```text
库存 R -= q，H 不变
预占 held -= q，released += q
订单项 reserved -= q，open += q
```

取消会增加 cancelled，属于 M3 的另一种业务动作。不能通过释放把客户订单默默取消。

释放请求按预占记录指定正数量，不能超过当前 held，不能重复提交同一个 reservationId 作为两行。不同键重复释放同一份已释放数量会被拒绝；原键重试则返回已经保存的结果。

完全释放后 `held=0`、`active_flag=0`。数据库 CHECK 同时保护这个关系，后续到期扫描才能避开已经结束的历史记录。

`expire_at` 按 UTC 保存。M2 只支持手工释放（包括已过期记录）；自动到期扫描属于 M4。后续扫描必须用 UTC 当前时刻比较，不能直接把本地时区的 SQL `NOW()` 当成 UTC。

## 7. 为什么旧 ERP 入口也必须改

已有 H=10、R=8 时，可用量只有 2。旧系统只检查 H≥出库量，会允许再出 3，导致 H=7、R=8，已经承诺的订单无法履行。

公共库存更新现在检查：

```sql
UPDATE erp_stock
SET count = count + :delta
WHERE tenant_id=:tenant AND id=:id
  AND count + :delta >= ful_reserved_count;
```

这是参数化 SQL。普通出库、调拨调出、盘亏、采购退货，以及撤销入库/盘盈/销售退货等减少 H 的动作，全部遵守它。增加 H 的动作不会自动替等待订单重新分配。

八个生效入口先构建本次全部库存变化，再批量锁定库存。调拨需要两仓的锁，不能先扣调出仓，再去发现调入仓的锁。

旧 ERP 自身的源单/单据状态锁仍在库存锁之前。M2 统一的是共享库存键的升序取得，并未把全系统所有表重排成完全相同的绝对锁顺序。新履约命令不修改这些未托管旧单据；M3 接入新发货适配器时要再次审查依赖。

## 8. 为什么给事务加注解还不够

旧库存代码先普通查询余额，再执行增量 SQL，最后用“旧余额+变化量”生成流水。即使余额 SQL 没超卖，两事务并发时仍可能把流水的新余额算错。

现在公共服务使用当前读锁住库存行，从已锁定的真实余额计算 after，并在同一事务插入 ERP 流水。所有相关库存的锁在逐行写之前取得。

真实测试逐条核对：

```text
ERP 逐笔 delta 的累计值 = 每笔流水 total_count = 最终 H
预占逐笔 held_delta 的累计值 = reserved_after = 最终 R
所有预占 held 的汇总 = R
0 <= R <= H
```

还专门检查首次入库并发创建：唯一库存身份加 upsert 后重读，只形成一条余额行，两个 0.000001 合成精确的 0.000002。

## 9. 重试为什么必须在事务外面

```text
外层重试
  第一次：新事务 → 锁失败 → 整体回滚
  短随机退避
  第二次：重新进入事务代理 → 重新校验与读取 → 提交
```

不能在已经回滚、或已经被标成 rollback-only 的事务里继续重跑一条 SQL。

当前最多三次，只重试锁失败。业务校验错误不重试。如果方法已经加入外层事务，就向外抛出锁错误，让最外层决定是否重试，不在内部额外开独立提交。

新命令由控制器外层调用重试组件，再进入履约事务代理；旧 ERP 的事务服务由一个位于事务拦截器外侧的切面包裹。业务原子范围不拆开。

本次测试实际占住库存行超过配置的锁等待时间，观察到“next attempt=2”的服务端日志，再释放测试锁。新命令与旧出库审核最后都只留下一个业务效果。此前仅凭“等锁后成功”不能证明发生过重试，因此测试还断言真实连接参数与重试日志。

## 10. 为什么不用 double

`9007199254740992.000001` 已超出 double 能精确表示全部小数的范围。原 ERP 库存汇总经过 double 转换，这一步会丢失精度。

当前 SUM 直接由 JDBC 映射为 BigDecimal，策略也全程使用 BigDecimal。真实数据库验证了上述数值、百万分之一以及 DECIMAL(24,6) 最大合法值 `999999999999999999.999999`。

新接口的数量、金额、ID 用字符串表达。前端不能再把这些数量转成 JavaScript Number 后当作精确库存依据。

## 11. 非法旧单据也不能制造库存

部分基座草稿允许存入负数量。若直接把负的出库量取反，就会增加库存。因此库存生效入口检查自然数量必须为正；盘点允许正负差额，但必须满足 `actual−stock=count`，账面和实际数量不能为负。

这项校验在审核/反审核的事务内，失败会连同状态变化一起回滚。为兼容既有历史检查，M2 没有重写所有 ERP 草稿保存规则；非法草稿不能产生库存效果。

1. `AllocationContracts`：命令和结果分别表达什么。

## 13. 面试时可以怎样讲

> 我在 ERP 实物库存上增加预占汇总，并用履约预占明细和追加流水解释每次承诺。分配在持有最新库存行锁后运行确定性策略，本次所有商品都满足才写入。旧 ERP 的出库、调拨、盘点和退货也统一检查 H≥R，并批量按库存键取锁。我用两个 JVM 竞争同一个 MySQL，验证了限量分配、同键重复请求、首次建行、旧入口竞争与锁超时后的整事务重试，同时核对余额和逐笔流水。

追问时先拿真实案例解释 H/R/A，再讲 SQL、隔离和锁；不要把少量并发正确性实验说成压测，也不要说已经完成发货、物流、自动过期或可靠消息。
