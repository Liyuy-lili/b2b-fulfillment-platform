# M3：部分发货、取消与物流闭环

> 阅读语境：以下正文记录该阶段当时的实现和取舍，早期“后续待做”仅为历史状态。当前M0—M7已经完成，请结合[现行总目录](../README.md)与系统教程。工程验收原件未改。

本阶段从“占住库存”推进到“真实出库并结束订单”。设计边界见 [ADR-012](../05-设计决策与复盘/ADR-012-M3-发货取消与物流集成.md)，阶段是否完成以 [项目进度](../09-项目规范与进度/PROJECT_STATUS.md) 和实际验收证据为准。

## 1. 先推演一笔 10 件订单

同一商品有两个仓库，A 有 6 件，B 有 8 件，客户订购 10 件。

| 操作 | A：H / R / A | B：H / R / A | 订单数量与状态 |
| --- | --- | --- | --- |
| 绑定 | 6 / 0 / 6 | 8 / 0 / 8 | open=10，NEW |
| 优先级分配 | 6 / 6 / 0 | 8 / 4 / 4 | reserved=10，RESERVED |
| 从 A 发出 4 | 2 / 2 / 0 | 8 / 4 / 4 | shipped=4，reserved=6，PARTIALLY_SHIPPED |
| 取消剩余 6 | 2 / 0 / 2 | 8 / 0 / 8 | shipped=4，cancelled=6，PARTIALLY_CLOSED |
| 物流签收 | 保持 | 保持 | 发货单 DELIVERED；订单仍为 PARTIALLY_CLOSED |

始终有 `ordered=open+reserved+shipped+cancelled`。不同商品可能按件、千克等计量，不能把不同商品的数量合成一个可发货量。

取消没有把商业订购量 10 改成 4；它保存客户当时订购 10、实际发出 4、后来取消 6 的完整事实。

## 2. 发货为什么要同时降低 R 与 H

预占表达“承诺给订单”，实物库存表达“仓库还剩多少”。货物已经出库，就不能继续作为未发货预占。

从 A 发 4 时，在同一事务中：

```text
held 6 → 2
consumed 0 → 4
库存 R 6 → 2
ERP 审核出库，H 6 → 2
订单 reserved 10 → 6，shipped 0 → 4
发货记录、ERP 出库明细、实物流水、预占流水互相关联
命令结果一起提交
```

A 的可用量仍为零：剩下两件仍然被订单预占。**发货不是先释放给其他人，再开启另一个事务扣库存。**持有库存行锁的同一事务覆盖两个变化，中间状态不会被并发写命令拿来分配。

实物 H 仍只有 ERP 库存流水服务修改。履约服务只改预占，再调用 ERP 内部端口；不能自己扣一次 H，随后 ERP 审核再扣一次。

## 3. 从请求到数据库的真实调用链

代码位于 `backend/yudao-module-fulfillment/src/main/java/cn/iocoder/yudao/module/fulfillment/`。

```text
FulExecutionController.ship
  → DatabaseCommandRetry（事务外）
  → FulExecutionService.ship（事务代理）
  → 命令记录 → ERP 源单 → 履约主单/明细 → 预占 → 有序库存锁
  → 重新校验数量、仓库、当前时间与 expire_at
  → R/held 转 consumed
  → ErpManagedSaleOutPort.createAndApprove（MANDATORY）
      → ERP 根据冻结源单生成出库与商业字段
      → ERP 更新原销售单的出库累计
      → ERP 审核与原库存流水服务，唯一扣 H
  → 保存发货与两套流水关联、订单汇总、幂等结果
  → 提交
```

一次发货限一个仓库。请求只指定预占和数量，不能让客户端指定商品、价格、税率或打开内部绕过开关。

新建 ERP 出库只有当前事务能看见。旧 ERP 单据自己的锁仍保留，但托管源单的手工创建、编辑、撤销和删除继续被拒绝。M3 重新审查了共享锁依赖；不能据此保证所有未来流程都不会死锁。

## 4. 内部端口怎样复用基座

端口位于 ERP 模块 `service/sale/managed/ErpManagedSaleOutPort.java`，由 `ErpSaleOutServiceImpl` 实现。ERP 不依赖履约 Maven 模块。

- 公共手工入口继续执行 `assertMutable`，遇到托管订单拒绝。
- 内部端口执行 `requireManaged`，从当前租户源单取冻结明细，并验证仓库及单位。
- 创建、金额计算和审核库存变化复用原 ERP 内部实现；没有复制第二套扣实物库存算法。
- 内部端口要求已经存在事务，不能由它另开一个先提交的独立事务。
- 没有全局“允许绕过”线程开关，控制器也没有 `internal=true` 参数。

金额沿用基座 MoneyUtils 的逐出库明细、税额、优惠计算与舍入规则。多次部分发货的金额舍入不是自行宣称的清结算系统。

## 5. 出错之后哪些东西回滚

本阶段使用隔离的 `fulfillment-fault-test` 配置验证两处失败：ERP 审核过程中的库存批次写入后，以及 ERP 审核返回后、履约发货落表前。故障控制来自服务启动配置，没有开放请求参数或匿名故障接口。

失败后必须同时看到：

- H/R 回到操作前。
- held、consumed 与订单数量回到操作前。
- ERP 出库、出库明细和本次实物流水没有留下。
- 发货和本次预占流水没有留下。
- 幂等命令记录也回滚，相同 key 可以在正常实例安全重试。

Redis 单号序列不属于 MySQL 事务，因此失败可能留下单号空档；不能将单号连续当成事务成功标准。我们检查数据库业务事实，而不是强求回滚 Redis 序列。

## 6. 取消与释放的区别

释放预占：`reserved → open`，订单仍然需要履约。

取消订单项：先 `open → cancelled`；不足部分再按预占 ID 的稳定顺序做 `reserved → cancelled` 和 `held → released`。R 同量降低，H 不变，逐订单项保存取消数量、原因与操作者。

取消量上限为 `open+reserved`。累计 shipped 不会被取消减小；已经发出的货物，后续通过 M4 退货表达。

发货与取消竞争时，双方都先锁相同源单和履约主单，后获得锁的一方使用最新数量判断。不能先读旧数量，再各自执行互不相干的写入。

旧 ERP 查询新增逐行 `fulfillmentRemainingQty=open+reserved`、`fulfillmentCancelledQty` 和托管标志；页面中托管订单不能被选入手工出库。商业订购量与已发生出库量保留原意义。

## 7. 预览为什么不等于库存承诺

`FulWorkbenchService.preview` 复用 M2 的纯计算策略，返回策略版本、库存 H/R/A 和计划。它不创建命令、预占或流水，也不持有库存写锁。

预览后库存可能变化。正式分配仍必须拿锁并重新算，不能提交前端传回的“预览结果”直接承诺库存。首版仍是本次所有 open 满足才新增预占。

## 8. 物流通知如何可信且可重复处理

本项目使用本地物流模拟器，不连接真实物流公司。管理页面发出的模拟动作，会通过本机 HTTP 调用实际匿名回调入口，经过真实验签和数据库事务。

签名内容：

```text
timestamp + 换行 + eventId + 换行 + 原始 body 字节
```

使用 HMAC-SHA256、常量时间比较和五分钟时间窗口。时间戳是 Unix 秒；重试可以更新签名时间，但 eventId 和事件业务内容保持一致。签名检查针对原始字节，业务去重摘要来自规范化事件内容。

服务端用 integrationId 映射租户、provider 和密钥。请求体/租户头不能指定回调所属组织；验签后进入可信租户上下文，结束时恢复原上下文。

| 情况 | 行为 |
| --- | --- |
| 同 eventId、同内容 | 返回原结果，不重复改变状态 |
| 同 eventId、不同内容 | 保存冲突次数和摘要，再返回冲突错误 |
| 已签收后迟到运输中 | 记录事件，不回退签收 |
| 错误签名、过期时间、未知集成 | 拒绝，不改业务 |
| 集成租户找不到该发货 | 返回可重试业务错误并保留日志诊断，不创建无来源发货 |

`DELIVERED` 是物流状态；订单 `FULFILLED` 是全部出库完成。两者分别建模。回调服务不调用任何库存减少逻辑。

密钥从外部配置读取。本地配置有公开的演示默认值；共享部署时应替换，不把本地模拟环境写成已接入生产物流。

## 9. 页面与代码怎样对照

1. ERP 系统 → 履约订单 → 详情，先看每行 ordered/open/reserved/shipped/cancelled。
2. “分配库存”选择候选仓库，先预览，再确认分配。
3. “预占与发货”选择同一仓库的记录，填写本次数量、承运商、物流单号，确认发货。
4. “取消未发货量”填写各订单项的取消量和原因。
5. “发货与物流”展开 ERP 关联和事件记录，模拟运输中、签收。

前端 `FulfillmentWorkbench.vue` 保留字符串数量，比较和加法通过定标 BigInt，避免用 Number 计算业务数量。网络失败的相同内容重试保留请求编号；已保存幂等响应是原命令的结果，当前数量仍应通过详情刷新查询。

发货查询按订单分页；物流事件和取消历史目前各显示最近 100 条，预占历史沿用按单查询。权限仍为功能、租户和订单归属；M6 再实现细粒度仓库授权。

## 10. 面试讲法与自测

可以说：在芋道 ERP 上二次开发履约命令，通过同库事务协调预占消耗与 ERP 出库，保持实物库存单一写入路径；实现部分发货、取消、物流验签去重，并用双 JVM 竞争和故障注入验证重复请求及回滚。

不要说：从零写了整个 ERP、实现了跨库分布式事务、已接入真实物流、能承载某个尚未压测的 QPS。

两道自测：

1. 为什么发货前降低 R 不会把库存让给其他订单？请说明锁和事务提交的位置。
2. 客户已发货 4 件、取消 6 件，物流后来签收，订单和发货单分别是什么状态？H/R 是否再变化？

自动到期释放、退货和定期核对是 M4；可靠消息与恢复是 M5；细粒度仓库授权是 M6。当前不提前把它们写成已实现。
