# 八分钟演示与排障

## 1. 先选对环境

日常主项目是15173/48080、库fulfillment、Redis DB0。最终独立交付使用15174/48082、新schema、Redis DB13和同名独立vhost。两套环境的ID相同也不是同一笔业务，不能混用Token或编号。

最终演示的实际路径、库和编号读取[最终交付结果](../10-验收证据/M7-final-release.json)中的`release_directory/database/demo`；固定数据副本为[M7-final-demo.json](../10-验收证据/M7-final-demo.json)。这些文件只有真正完成执行后才构成证据；不要从历史M7.1文件猜最终编号。

日常主库可看历史履约229的消息演示和M6文件任务。要演示全新固定闭环，使用最终独立包。主项目已存在的数据不要通过重新初始化清掉。

## 2. 上台前五项准备

1. 用交付手册启动已安装的独立包；Start只启动应用，不会再初始化数据库。
2. 确认端口和真实登录API返回`code=0`。仅看进程存在或HTTP200都不够。
3. 在演示窗口重新登录对应环境，租户“芋道源码”，本地admin/admin123；只读账号m7warehouse/admin123。
4. 读取demo.json中的sourceOrder、bound.orderId、warehouseA/B、product、shipped和文件任务ID。把界面筛选清空或设为正确编号。
5. 保留库存XLSX与错误CSV作为服务启动异常时的静态证据。它们是预先真实生成的文件，不能讲成正在实时执行。

## 5. 被要求演示故障时

不要在主库或最终演示库注入SQL污染、改MQ消息或运行故障profile。打开M7报告对应的测试库证据，展示真实退出码、日志时间、恢复后的SQL断言。若面试官要求重跑，使用tests/m7_run_all.ps1指定一个case并提前说明会创建新测试库、需要启动多JVM。

```powershell
# 项目根目录，正常依赖已运行；只操作新M7测试schema和专用Redis DB12
./tests/m7_run_all.ps1 -Cases message
./tests/m7_run_all.ps1 -Cases filefoundation
```

file完整恢复套件要求先运行filefoundation，再运行file；两者共享SQL库和Redis DB12单号序列，中间不能FLUSHDB。编排脚本已保留这一状态；本轮一次编排失败及只恢复测试序列的证据见[M7.2序列修复](../10-验收证据/M7.2-sequence-repair.json)。不能将旧foundation配新jar当成同次实验。性能脚本要求本轮正确性门禁通过；不要与回归同时运行后拿数字作比较。

## 6. 排障按证据定位

| 症状 | 先查什么 | 不应怎么处理 |
| --- | --- | --- |
| 页面显示旧数据/无权限 | 当前URL、schema、Token所属环境、筛选条件、code | 不关闭鉴权来展示 |
| 后端启动失败 | owned进程日志、端口归属、Flyway validate、依赖连接 | 不修改已执行V1—V8 |
| Redis AUTH错误 | 空密码是否被显式传为AUTH、redisDatabase是否正确 | 不FLUSHDB0 |
| Outbox不动 | messages开关、vhost、连接错误、attempts、lease与lastError | 不直接把状态改SENT |
| Broker已确认但未消费 | Inbox/失败重试状态、消费者开关、队列与读模型版本 | 不把confirm当消费成功 |
| 任务等待/重试 | 数据库准入、租约、工作者开关、创建人是否停用、授权是否撤销 | 不无限扩线程或改RUNNING |
| 文件下载失败 | 当前权限、登记SHA/大小、storage-root、文件是否存在 | 不开放整个私有文件静态目录 |
| 核对出现差异 | 先保存报告、核对事实链、说明是否测试注入 | 不用确认按钮伪装自动修复 |
| 安装拒绝已有库 | 确认是否正在误做“重新安装” | 不删除数据库绕过门禁 |

## 7. 重启和数据保留

正常启停见[交付手册](../06-运行交付与证据/独立交付运行手册.md)。停止应用保留schema/vhost/Redis/私有文件。最终验收记录正常依赖重启和原key重放，不代表断电测试。备份必须同时考虑数据库、Redis单号序列、Broker持久化数据、私有文件和受保护配置；只保存jar不能恢复业务。
