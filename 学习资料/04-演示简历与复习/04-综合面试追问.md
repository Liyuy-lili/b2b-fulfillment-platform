# 综合面试追问：先业务，再机制，再证据

本篇补齐M4.3—M7，并把核心库存问题串起来。专题题库已升级到M7，共192题，本篇另保留40道综合追问。回答时先举当前业务例子，再讲代码与限制；没有运行的环境不作性能承诺。

## A. 建模、事务和并发

<a id="x01"></a>

### 1. 为什么单独建立履约单，不直接给ERP销售单加状态？

ERP销售单是商业承诺，履约还有预占、分仓、部分发货、取消和退货的独立事实。一项订单可能有多个预占/发货/退货，单个状态不能还原数量。绑定保留ERP原编号和明细快照，托管后冻结会破坏快照的旧编辑入口。代价是多表约束和投影维护，不能凭空制造第二份实物库存。

追问：价格改变怎么办？当前托管源单不支持旧入口任意修改；新的变更业务需要另行设计，不直接改快照掩盖历史。

<a id="x02"></a>

### 2. 为什么预占不直接减实物库存？

预占说明这批货不能卖给其他订单，实物仍在仓内。H6/R6发4后是H2/R2，取消剩余2后是H2/R0。若分配先减H、发货再减H，就重复扣减；若只记Redis，旧ERP出库可能完全不知道占用。

<a id="x03"></a>

### 3. 怎么避免“查到足够，随后被别人抢走”？

计划在事务内对有序库存进行当前读/加锁，检查H−R再写R和预占。多商品分配必须一起成功或回滚，不能在第二个商品不足时留下第一个商品的占用。HTTP预览只是提示，不承诺库存；确认分配要重新校验。

<a id="x04"></a>

### 4. 为什么不用一把Redis分布式锁？

现有事实在同一MySQL里，数据库事务/行锁/约束能把订单、R、流水和ERP写入一起提交。加Redis锁仍要处理锁失效、旧ERP绕过和跨资源原子性。当前没有把Redis锁作为库存正确性的前提；Redis主要复用登录与单号等基础能力。

<a id="x05"></a>

### 5. RC下怎么保证正确？

写路径依靠明确行锁、当前读、唯一约束和条件更新，不依赖同一事务普通SELECT反复看见旧快照。采用RC还与旧ERP托管空记录检查的间隙锁风险有关，选择来自本项目受控并发观察。不能把“RC更快”当成所有系统都适用的结论。

<a id="x06"></a>

### 6. 同key并发怎么返回同一个结果？

数据库唯一命令身份让一方先提交，另一方读取已提交命令并比较规范化摘要，返回保存的响应。同key不同参数明确冲突。遇到可重试数据库冲突，在外层重新开启整笔事务，不重复保存半成品。授权检查仍然生效，旧key不是永久通行证。

<a id="x07"></a>

### 7. 为什么ERP适配必须MANDATORY？

防止被无事务直接调用并独立提交。发货中ERP单据/库存流水、履约发货事实和Outbox必须属于同一事务；适配端口若使用REQUIRES_NEW，外层失败也无法撤回已扣H。故障测试在ERP写前/后抛错，对比完整余额和事实。

<a id="x08"></a>

### 8. 分仓策略怎么保证稳定？

输入校验、启用/授权仓库、固定仓库排序、固定商品/明细处理顺序。PRIORITY_SPLIT按优先级拆分，SINGLE_FIRST先找能满足整单的仓再按规则回退；相同库存和规则版本给相同结果。确认时库存可能变化，所以预览结果不是锁定承诺。

<a id="x09"></a>

### 9. 部分发货与取消同时发生怎么办？

锁住同一订单/明细和预占，使两笔事务串行检查余量；请求合计超过可处理量时只能有合法赢家。发货消耗held并由ERP扣H；取消先消耗open，再释放held，不撤销已经发出的gross shipped。最终项级恒等式要成立。

<a id="x10"></a>

### 10. 到期扫描查到一条预占就能释放吗？

候选扫描无锁，正式命令重新锁定并判断期限、held及订单状态。候选可能过期或被发货/延期改变，不能把扫描结果当事实。到期仅释放剩余占用，失败回滚等待补扫；后台不是硬实时承诺，禁用租户恢复后补扫。

<a id="x11"></a>

### 11. 为什么退回后shipped不减少？

shipped表示历史发出总量，returned表示已实际收回；两者都应追溯。把shipped减掉会破坏原发货上限和旧ERP关联。申请额度受原发货约束，REQUESTED和RECEIVED共同占额度，拒绝释放申请额度；实际收货才通过ERP增加原仓H。

<a id="x12"></a>

### 12. 有CHECK约束还需要代码检查吗？

需要。代码提供业务语义、权限、跨行校验与可读错误；数据库约束兜住单行非负、状态、唯一性和同租户关联。两层范围不同，CHECK不能检查跨表汇总等式。负向约束探针必须rollback，不留污染。

## B. 消息和租约

<a id="x13"></a>

### 13. 为什么直接在事务里发MQ不够？

数据库回滚但MQ已收会产生假事件，数据库提交但网络失败又可能漏通知。Outbox和业务同库提交，发送独立恢复；它不要求MySQL与RabbitMQ分布式事务，也不能让网络发送本身只发生一次。

<a id="x14"></a>

### 14. confirm、return、ACK分别说明什么？

confirm是发布端收到Broker确认，return说明mandatory消息没有合适路由，ACK是消费端确认本条交付可由Broker移除。当前消费失败可以先持久化本地重试再ACK，所以ACK也可能意味着重试接管，不能等同于投影已成功。

<a id="x15"></a>

### 15. Broker确认后、标SENT前崩溃？

租约到期后重新发送同eventId；允许重复投递。Inbox唯一身份和投影版本阻止重复业务效果。M7相应测试使用真实exit71，恢复后观察尝试数、单Inbox和业务事实不重复。

<a id="x16"></a>

### 16. 消费提交后、ACK前崩溃？

Broker可能重投；Inbox已提交的PROCESSED使重复交付不再更新投影。真实exit72验证这个窗口。若把ACK放在本地事务提交前，进程崩溃可能失去处理机会。

<a id="x17"></a>

### 17. 消费一直失败会怎样？

投影事务回滚；失败状态另事务持久化RETRY_WAIT，按有界次数退避，最终DEAD；人工重试有独立权限和审计。连失败记录都无法提交就不能ACK。坏JSON/不可信租户等不作为正常可重试业务，进入DLQ。

<a id="x18"></a>

### 18. 订单事件乱序如何处理？

事件带aggregateVersion，投影仅接受更高版本，旧版本只完成去重。此规则适用于当前完整执行快照；如果以后事件改成“余额加1”这种增量副作用，仅比较版本可能丢中间增量，需要重新设计，不能机械复用。

<a id="x19"></a>

### 19. 租约为什么还要version？

只看过期时间，旧工作者可能在新工作者接手后回写成功。领取递增version并记录owner，完成时带owner/version CAS；旧结果返回LATE或不匹配，不能覆盖新状态。租约不是永久互斥锁，也不会阻止旧进程继续做网络发送，因此下游仍需幂等。

<a id="x20"></a>

### 20. 人工重发和重建为什么分开？

REPUBLISH重新发送原事件，保持eventId和正文；RETRY_CONSUME只调度本地失败消费；REBUILD读取当前事实生成投影，不伪造历史事件。权限、原因和审计各自明确，同key重放受理结果稳定，不随后台完成而变成另一个响应。

<a id="x21"></a>

### 21. 项目是否exactly once？

不这样承诺。跨DB与MQ至少一次传输，本地Inbox和事务保证当前投影幂等。未来若增加短信/支付等外部副作用，对方也需要业务身份幂等或可恢复协议；当前没有验证这些外部系统。

## C. 异步任务和权限

<a id="x22"></a>

### 22. 为什么不用@Async直接导入？

纯内存任务进程重启会丢排队与进度，也不便限租户并发。当前先持久化任务与输入文件，数据库准入加有界线程池，领取租约后执行；进程退出可重新领取，已成功行被跳过。

<a id="x23"></a>

### 23. 同CSV换个任务再导入会重复下单吗？

任务key只解决提交重试，还需要跨任务业务身份。tenant/sourceSystem/externalNo唯一，同内容摘要复用原草稿，改变数量等内容冲突。文件SHA一样不代表业务去重边界正确；不同文件也可能包含相同外部订单。

<a id="x24"></a>

### 24. 一行写完ERP后进程退出怎么办？

ERP草稿、身份记录和行结果在该行事务共同提交。提交前退出整体回滚；提交后退出重启读取成功行并跳过。真实exit81在行提交后退出，确认最终一份草稿；不能靠内存行号保证。

<a id="x25"></a>

### 25. 取消导入会回滚已成功的行吗？

不会。它是持续的逐行任务，取消在边界停止后续工作，保留已成功草稿和待处理行。已经完成的独立业务不能假装被整批原子回滚。当前也不自动批准或履约导入草稿。

<a id="x26"></a>

### 26. 导出怎么控制内存？

冻结最大源ID，按主键游标分批读取并流式写XLSX，限制输出行数/字节；执行器和队列有界。M7实际记录采样堆、GC、RSS、文件大小和总耗时。采样峰值不是精确瞬时峰值，也不能据此声称永远不会OOM。

<a id="x27"></a>

### 27. 导出是不是一个一致时点？

不是。最大ID限制后续新增行进入，但分批读取时已有记录可能改变。导出元数据明确边界。核对采用独立RR快照是另一个业务；给长导出套长事务会增加undo/连接占用，不能无成本获得一致快照。

<a id="x28"></a>

### 28. 旧工作者导出完成得更晚怎么办？

文件按租约产生独立路径，发布结果引用前CAS当前owner/version，旧文件不能覆盖新结果。当前可能留下未引用的私有孤儿，尚无自动清理；后续清理应检查数据库引用、租约与保留期。

<a id="x29"></a>

### 29. 下载只检查提交时权限够不够？

不够。用户可能被停用或撤销仓库范围，结果文件仍含敏感内容。执行、重试、控制和下载都要重新检查当前授权；返回文件ID不是授权凭证。私有文件不能通过静态URL绕过检查。

<a id="x30"></a>

### 30. 功能权限与仓库范围如何组合？

先有对应功能权限，再限定本租户与允许的仓库，OPERATE区别于READ，必要时还检查订单归属。仓库专用投影不返回价格。当前未统一改造全部上游ERP查询，专用仓库角色不能额外授予广泛ERP价格/客户权限。

<a id="x31"></a>

### 31. 线程池为什么会串租户？

ThreadLocal随线程存活，线程池复用时上个任务的租户/actor若未清理，下一个任务可能带错上下文。每次设置前保存上下文，finally恢复/清理；测试让同一实际工作线程先后执行不同租户，观察上下文和结果。

## D. 核对、性能和交付

<a id="x32"></a>

### 32. 核对为什么用RR，写业务用RC？

写业务依靠锁保证并发；核对需要多表读取同一事实视图，避免一半读到发货前、一半发货后。独立Bean建立只读RR快照，外层RC负责报告命令。不能把快照时间戳当历史查询功能，也不能忽略一次占两条连接的成本。

<a id="x33"></a>

### 33. 发现差异为什么不自动修复？

缺一条流水、错R或外部写入可能有不同原因，自动改总量可能掩盖真实业务。当前保存expected/actual与规则、人工说明；ACKNOWLEDGED只表示已看过，不表示修复。测试污染在独立库finally恢复，主库不演示篡改。

<a id="x34"></a>

### 34. 订单查询为什么加这个联合索引？

现有查询有tenant/deleted/status等值条件并按id倒序，索引(tenant_id,deleted,status,id)匹配过滤和排序。原计划可能选择PRIMARY倒序并跳过其他租户/状态大量行；必须看实际EXPLAIN，不能先编造filesort。最终报告保存ANALYZE的实际行和HTTP样本。

<a id="x35"></a>

### 35. 为什么before/after用索引可见性切换？

同一JVM和数据中INVISIBLE模拟旧可用索引集合，VISIBLE使用新增索引，交替多轮并热身，减少JIT/启动差异。两种状态都维护物理索引，因此它比较的是读计划，不是建索引前后的写入成本；写放大只定性说明，不编造写入提升。

<a id="x36"></a>

### 36. SQL更快为什么HTTP不一定同比提升？

鉴权、连接池、JSON、日志、网络和count查询都占时间；P99还受GC与调度影响。要记录查询次数和扫描行，再分开看SQL与端到端结果。小样本、同机客户端和数据分布都限制外推。

<a id="x37"></a>

### 37. 库存不足算请求失败吗？

是正常业务结果，需与HTTP错误/500/超时区分。H32时64个订单各抢1件，合法结果是32成功、32不足，最终R32；释放后R0/H32。高QPS但破坏恒等式没有价值。成功QPS、总请求吞吐和业务不足率不能混成一个指标。

<a id="x38"></a>

### 38. 性能实验有什么不足？

单机、共享本机MySQL、有限JVM与连接池、本地HTTP客户端、明确合成数据和短窗口；不是生产容量规划。全局InnoDB锁计数可能受共享服务其他活动影响。GC按采样统计，单次导出不写提升百分比，未测冷缓存/跨机/极限稳定时长。

<a id="x39"></a>

### 39. 为什么迁移只能新增V8？

已经执行的V1—V7有校验和与历史，修改会破坏可重复升级和Flyway validate。V8只新增索引，主库升级前后逐行事实/Redis快照保持，旧历史完全相同。回滚应用不等于自动撤销数据库DDL，需要明确兼容策略和备份。

<a id="x40"></a>

### 40. 独立交付证明了什么？

生产前端、jar、SQL、脚本、MIT和manifest能在源码外的新目录/新schema运行，运行不依赖源码node_modules/Maven/pnpm；仍依赖明确版本Java/Node/MySQL/Redis/RabbitMQ。正常重启与同机新目录验证不等于新OS安装、跨机部署或断电恢复。
