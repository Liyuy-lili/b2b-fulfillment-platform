# 07 旧ERP库存入口的统一保护

> 最终集成（2026-10-20）：M7已用最终jar复测八类旧入口和竞争；专用仓库ACL不代表全部上游ERP权限重写。公共库存H≥R规则在所有原生库存生效边界继续成立。

业务主线：[M2决策](../05-设计决策与复盘/ADR-011-M2-预占与统一库存写入.md)、[旧入口验收](../10-验收证据/M2-legacy-inventory.json)。代码：ErpStockRecordServiceImpl、ErpStockServiceImpl、ErpStockMapper。

## 1. 为什么新模块正确仍可能卖不出货

H10/R8，已有订单承诺8，普通ERP出库想拿5。只检查H≥5会通过，结果H5/R8，承诺比剩余货多3。正确的是普通减少只能消耗H−R=2。

调拨出库、盘亏、采购退货、入库反审核也能减少H。只保护销售出库会漏掉其他入口；既有功能仍然在同一库存事实之上。

## 2. 八类业务及反向影响

| 类别 | 审核库存效果 | 反审核或撤销的相反方向 |
| --- | --- | --- |
| 采购入库 | 增加H | 减少H，也必须保护预占 |
| 采购退货 | 减少H | 增加H |
| 销售出库 | 减少H | 增加H；托管单公共撤销仍拒绝 |
| 销售退货 | 增加H | 减少H；托管单公共操作仍冻结 |
| 其他入库 | 增加H | 减少H |
| 其他出库 | 减少H | 增加H |
| 调拨 | 来源仓减少、目标仓增加 | 来源仓增加、目标仓减少 |
| 盘点 | 按实际−账面差额增减 | 反向差额 |

同一业务可能涉及多行和多仓，应该先知道全部StockKey，再按顺序锁完，然后逐项更新和写流水。不能一边遍历明细一边随机取得跨仓锁。

## 3. 当前公共路径

```text
业务审核/反审核事务与源单/单据锁
→ createStockRecords(所有本批变化)
→ lockStocks(去重并排序的商品/仓库键)
→ createStockRecord
→ updateStockCountIncrement
→ 当前读余额，验证H+delta >= R
→ changePhysical条件更新
→ 用本次精确after写erp_stock_record.total_count
```

代码中batch内调用同类createStockRecord虽然属于自调用，但**外层createStockRecords本身已在代理事务中**，不能机械地说任何自调用都会让整个批次没有事务。

## 4. 为什么先读余额必须用当前读

普通快照读可能来自早先状态；再生成流水余额，会导致库存表正确而流水total_count不正确。公共服务持有行锁读取最新余额，再计算after，后续流水用同一个结果。

SUM直接映射BigDecimal，避免先转double再构造BigDecimal。BigDecimal只能保留拿到的值，无法恢复上游已经丢失的小数。

## 5. 首次建行与唯一键

lockStocks要求活跃事务。createMissing=true时对缺行ensure，再重读加锁；唯一身份tenant/product/warehouse避免双行。预占用false，不凭空制造正库存；真实入库才增加H。

库存身份不允许逻辑删除后重建来绕过预占关系。数据库CHECK维护H≥R≥0，迁移发现负数/重复身份先拒绝，不自动合并脏数据。

## 6. 旧草稿与生效边界

一些基座草稿能保存负数量，但审核生效时必须检查自然数量为正。否则“负出库”取反会增加库存。盘点允许差额正负，但actual和stock非负、count=actual−stock。数量校验失败应把审核状态和库存效果一起回滚。

SKU基本单位创建后不可改，否则已有数量的单位解释变化，不能只通过页面展示修正。

## 7. 并发场景

预占8与旧出库5竞争H10：谁先拿锁谁按最新可用量处理；不能同时让R8和H5提交。调拨A→B与B→A按同一StockKey顺序取两仓锁，减少反向锁循环。

这里统一的是共享库存键顺序，不声称旧ERP全系统所有业务表已重新排序，也不声称完全消除死锁。最外层对悲观锁失败做有界整事务重试。
