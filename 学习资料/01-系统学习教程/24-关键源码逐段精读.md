## 1. 命令claim：先得到同一行，再比较内容

源码：FulCommandService.claim和FulCommandRecordMapper.ensure/lock。

```java
String hash=DigestUtil.sha256Hex(canonical);
mapper.ensure(type,tenant,actor,key,hash,LocalDateTime.now(ZoneOffset.UTC));
var command=mapper.lock(type,tenant,actor,key);
if(!command.getRequestHash().equals(hash)) throw exception(IDEMPOTENCY_KEY_CONFLICT);
return command;
```

ensure使用INSERT ... ON DUPLICATE KEY UPDATE id=id，不覆盖已有hash；lock使用完整tenant/actor/type/key并FOR UPDATE。先前成功命令不能被后来异内容请求改写；并发ensure会围绕唯一身份等待。不能用insert影响行数猜“我是不是第一个”。

claim不独立提交，其插入、业务和complete响应都位于外层命令事务。若后续异常，命令也回滚；claim本身不是一把跨数据库或永久保留的全局锁。

练习：如果ON DUPLICATE直接覆盖request_hash，会有什么后果？异内容请求可能抹去原命令身份，摘要比较失去作用。

## 2. 分仓共享余额：同SKU两行不会双花

源码AllocationPlanner.plan：

```java
BigDecimal available=remaining.getOrDefault(key,BigDecimal.ZERO);
BigDecimal take=needed.min(available);
if(take.signum()>0) {
    pieces.add(new Piece(d.itemId(),d.productId(),warehouse,take));
    remaining.put(key,available.subtract(take));
    needed=needed.subtract(take);
}
```

remaining由商品/仓库Key定位，供全部需求行共享。输出保留d.itemId，供后续追溯。任一需求剩needed>0时返回false与空pieces，之前计算的部分计划不会拿出去提交。

这个函数不拿数据库锁；调用者allocate必须先锁真实库存并组装新供给。把纯函数测试通过解释成数据库竞争通过，是层次混淆。

## 3. SQL同时限制R的上下边界

源码ErpStockMapper.changeReserved：

```sql
UPDATE erp_stock
SET ful_reserved_count=ful_reserved_count+#{delta},
    update_time=CURRENT_TIMESTAMP
WHERE tenant_id=#{tenant} AND id=#{id} AND deleted=0
  AND ful_reserved_count+#{delta}>=0
  AND ful_reserved_count+#{delta}<=`count`
```

正delta是增加承诺，负delta是释放/发货消费。上界防承诺超实物，下界防重复释放负数；必须检查返回1。SQL只保证这一行余额，订单/预占/ledger一致仍由外层事务维护。

## 4. 发货now的位置就是业务语义

源码FulExecutionService.ship，先stockService.lockStocks后：

```java
LocalDateTime now=LocalDateTime.now(ZoneOffset.UTC);
if(amounts.keySet().stream().map(held::get)
    .anyMatch(r->!r.getExpireAt().isAfter(now)))
```

## 5. ERP端口的传播声明

源码ErpSaleReturnServiceImpl.receiveAndApprove，ErpSaleOutServiceImpl.createAndApprove同样要求MANDATORY：

```java
@Transactional(
    propagation=org.springframework.transaction.annotation.Propagation.MANDATORY,
    rollbackFor=Exception.class
)
```

接口只定义能力，真正事务声明在实现；调用必须经Spring代理。业务的源单/履约/库存锁与ERP审核继续处于同一事务。它防止错误调用者悄悄开启独立提交，但不能把任意远程数据库自动加入。

练习：如果改为REQUIRES_NEW，ERP成功后履约抛错，会留下什么不一致？源ERP库存已变，履约事实却回滚。

## 6. 到期候选不是最终裁决

源码FulExpiryService.expire，拿完库存锁后：

```java
LocalDateTime now=LocalDateTime.now(ZoneOffset.UTC);
if(r.getExpireAt().isAfter(now))
    throw new CandidateNotDueException();
```

这类异常不是库存不足的普通成功结果，而是让本次系统命令回滚。若保存“NOT_DUE”，同一reservation的固定系统key可能永久阻止真正到期；已关闭返回ALREADY_CLOSED则不同，原记录不会恢复held。

源码Scanner在进入每条处理前先推进afterTime/afterId；异常只记日志，下一页继续，到尾回绕。游标前进不能被当成业务已成功。

## 7. 额度SUM依赖写者协议

源码FulReturnItemMapper.committed的核心条件：

```sql
SELECT COALESCE(SUM(i.quantity),0)
FROM ful_return_item i
JOIN ful_return r ON r.id=i.return_id AND r.tenant_id=i.tenant_id
WHERE i.tenant_id=#{tenant} AND i.shipment_item_id=#{item}
  AND i.deleted=0 AND r.deleted=0
  AND r.status IN ('REQUESTED','RECEIVED')
```

SUM不带FOR UPDATE，并非天然串行。create/receive/reject均先锁共享源单/订单，才使各写者不能同时用同一旧额度提交；allowance只读不取得这种承诺。

退货收货把REQUESTED变RECEIVED，SUM仍计同一行一次，不是在已承诺量上再额外加一次。拒绝从集合中移除该申请。

## 8. 冲突诊断先提交再返回业务错误

源码FulLogisticsService.receive遇到同eventId异hash时增加conflict_count，返回outcome CONFLICT。Controller在retry.run代理调用完成后：

```java
return "CONFLICT".equals(result.outcome())
    ? CommonResult.error(CALLBACK_CONFLICT)
    : success(result);
```

返回值不是为了容忍冲突，而是把诊断保存和HTTP业务错误区分。若Service在修改后立刻抛出回滚异常，冲突计数也不保留。未知发货另走日志和可重试错误，不插孤立外键事实。

## 9. 前端perform保留不确定命令的key

源码FulfillmentReturns.vue.perform：

```typescript
const fingerprint = `${action}:${JSON.stringify(data)}`
let key = keys.get(fingerprint)
if (!key) {
  key = crypto.randomUUID()
  keys.set(fingerprint, key)
}
```

请求成功后删除该指纹key；catch保留供同内容重试，提示先刷新核对。这个Map是当前页面会话辅助，不是跨浏览器/数据库的权威幂等记录。后端原key重放和状态保护仍必要。
