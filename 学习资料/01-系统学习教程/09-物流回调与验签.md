# 09 本地物流HTTP回调、签名与乱序

> 最终集成（2026-10-20）：物流这条链仍是本地HTTP/HMAC，执行事件另走M5可靠MQ。运输/签收不额外扣H，也不都生成执行数量事件；不能把二者的确认机制混用。

物流连接本地模拟器，经实际HTTP进入同一回调入口，未接物流公司。M5已为执行事件引入MQ，但这条物流回调链本身仍走HTTP。入口FulLogisticsCallbackController.receive，状态事务FulLogisticsService.receive。

## 1. 为什么允许免管理端登录

物流服务没有后台用户登录态，但必须携带认证签名。配置以integrationId映射tenant/provider/secret；服务端不能信任body中的tenantId。@PermitAll不等于无认证，当前由自定义HMAC认证。

## 2. 实际契约

路径：POST /app-api/fulfillment/logistics/callback/{integrationId}，本地integrationId=local-demo。

头：
- X-Logistics-Timestamp：Unix秒。
- X-Logistics-Event-Id：业务事件ID。
- X-Logistics-Signature：HMAC-SHA256十六进制。

body含provider、eventId、shipmentNo、eventType、occurredAt；只接IN_TRANSIT/DELIVERED，时间带偏移。body事件ID与头一致，provider与配置匹配。

签名字节：
```text
timestamp + "\n" + eventId + "\n" + 原始body字节
```

LogisticsSignature限制时间偏差300秒、body最多8192字节，校验头格式与密钥长度，以MessageDigest.isEqual比较解码后的摘要。

## 3. 为什么签原始body

相同JSON语义重新序列化可能改变空格、顺序或时间格式。签名验证必须绑定收到的原始字节；业务去重摘要可以另对规范化业务字段计算。二者用途不同。

当前回调先验签，再解析/校验body，再建立配置租户上下文并验证租户有效，finally恢复原tenant/ignore，避免线程复用污染。

## 4. 去重、冲突和未知单据

唯一范围tenant+provider+eventId。相同事件同业务内容返回已处理结果；同ID但内容变了，增加conflict_count/last_conflict_hash。

冲突事务返回CONFLICT，Controller在事务已完成后映射业务错误。如果事务里先抛异常，刚写的冲突诊断也会被回滚。未知shipment记录日志并返回错误，不伪造发货单或插入孤立关联。

重试沿用eventId，可用新timestamp重新签名；业务摘要不包含易变签名头，因此不会被误判为新业务。

## 5. 配送状态单向演进

SHIPPED收到DELIVERED变已签收；已DELIVERED再收到运输中，只记录并返回IGNORED_AFTER_DELIVERED，不回退。重复签收不会产生第二次库存变化，因为回调从来不进入库存写路径。

回调只锁事件与发货，不去锁库存和原订单，缩小锁依赖。它不是替代发货成功的依据，更不能凭一个未知单号创建真实出库。

## 6. 证据与练习

看 [M3核心](../10-验收证据/M3-acceptance.json)、[签名单测目录](../10-验收证据/M4.2-junit)，从源码找签名篡改、旧时间、重复、冲突、未知单和乱序。Transport是HTTP，不要用publisher confirm/ACK解释当前回调。

自测：签名合法是否证明事件之前没处理？不证明，去重仍必要。相同body换timestamp重签是否新事件？事件ID/规范化内容相同仍是原事件。
