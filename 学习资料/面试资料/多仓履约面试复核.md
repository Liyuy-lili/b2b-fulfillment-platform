# 多仓履约面试复核

## 项目定位

适合 Java 后端校招项目面。用“把多仓履约接入已有 ERP，且不能破坏旧库存入口”讲主线：上游提供订单、出入库、登录与租户，本项目补充预占及统一库存约束、取消与发货、对账、消息恢复和文件任务。讲到个人分工时，根据实际参与说明 AI 辅助和自己能独立解释的部分。量化数据沿用原实验的负载、硬件、采样和对照口径。

公开牛客面经样本中，字节后台开发一面涉及并发防超卖，美团 Java 面经涉及消息丢失、重复消费、索引与分页，以及项目中使用 MQ 的理由。以下问题根据项目实现改写，样本用于准备追问，不用于估计出题概率。[字节面经](https://www.nowcoder.com/feed/main/detail/b3b25ab774ce47a7943ea9187f350706?sourceSSR=dynamic) · [美团面经一](https://www.nowcoder.com/feed/main/detail/3f1df06789e5449da0dbf30fb528db48) · [美团面经二](https://www.nowcoder.com/feed/main/detail/19f0468db70a428eba35cf73c84f9469?sourceSSR=users)

## 一面优先练的六题

| 追问 | 回答应覆盖 | 接着怎么追 |
| --- | --- | --- |
| 两个订单同时要同仓库存，怎么保证不超卖？ | H 是实物，R 是预占，A=H−R。先锁业务行，再按固定顺序锁库存行，锁内读取余额与分配，条件更新维持 H≥R≥0。Redis 不承担库存正确性。 | 两个 SKU 的锁顺序相反时怎么办？等待期间重新检查哪些事实？ |
| 旧 ERP 还允许出库，怎么防止绕过预占？ | 新旧入口争用同一库存行。ERP 库存写入口校验扣减后 H≥R。旧单审批、实物扣减、ERP 流水在同一事务里。发货先释放相应 R，再通过 ERP 扣 H 一次，整个操作共同提交。 | 旧出库先成功和预占先成功时，分别得到哪组 H/R？某条明细失败，审批状态会怎样？ |
| 超时后用户重试，如何区分同一次请求和误用幂等键？ | 命令以租户、操作者、命令类型、键唯一；规范化请求计算哈希。同键同请求返回已保存响应。同键参数改动返回冲突。记录、响应和副作用共同提交，重放仍校验访问权限。 | 客户端换了键怎么办？幂等记录回收后，重试窗口怎么定义？ |
| DB 已提交但 MQ 发不出去、消息已消费但 ACK 丢了，怎么办？ | 业务事务写 Outbox，发布端依据 confirm 和 return 记录结果。消费者按事件 ID 去重，读模型依据版本防倒退。解释发布确认后未更新 Outbox、消费提交后未 ACK 两个窗口，以及失败重试、DEAD 和人工恢复。 | 为什么 confirm 和 ACK 是两回事？经典队列的故障边界是什么？ |
| 加索引为什么加这四列，深分页现在还慢吗？ | V8 索引为 `(tenant_id,deleted,status,id)`，说明前三列过滤、最后一列支持顺序扫描，以及实际旧计划是 PRIMARY 反向扫描。引用 100001 条合成订单上的同数据 INVISIBLE/VISIBLE 对照，`OFFSET` 越深仍会多跳行。 | 状态筛选可选时能否复用排序？改成游标如何处理跨页有增删？ |
| 这个项目你究竟完成了什么，怎么证明？ | 从源单到取消或发货讲一遍，自己指到事务入口、库存更新 SQL 和实测断言。说明芋道复用、二次开发与自己实际做的事。 | 当场写出两个请求争抢库存的测试条件，指出哪条断言能发现只看 HTTP 会漏掉的错误。 |

涉及数据库锁与消息确认，技术定义可对照 [MySQL 锁定读](https://dev.mysql.com/doc/refman/8.0/en/innodb-locking-reads.html)、[MySQL 死锁处理](https://dev.mysql.com/doc/refman/8.0/en/innodb-deadlocks-handling.html)和 [RabbitMQ Publisher Confirms 与 Consumer Acknowledgements](https://www.rabbitmq.com/docs/confirms)。

## 从问题定位源码和实测

- **库存与死锁**。从 `FulAllocationService.allocate` 到 `ErpStockServiceImpl.lockStocks`、`ErpStockMapper`。看清固定的锁顺序和更新条件，再到 `DatabaseCommandRetry` 看有限次数、整事务重试。RC 本身不阻止超卖。旧 ERP 入口从 `ErpStockOutServiceImpl.updateStockOutStatus` 查到扣减和记录流水。
- **幂等与到期**。从 `FulCommandService.claim` 到 V1 的 `uk_command_key`。再对照 `FulExpiryService` 如何在获得锁后检查预占仍活跃且已到期。进程扫描与发货并发时，以锁内事实决定还能释放多少。
- **发布与消费**。从 `FulOutboxService.append` 到 `FulMessageWorker`、`FulRabbitTransport`、`FulMessageConsumerService`，分别找出事务提交、发布确认、消费提交、ACK。故障演示看 [恢复与监控](../../项目代码/docs/履约监控与故障验收.md)。
- **扩展追问**。从 `FulReconcileSnapshotReader` 区分库存核对的一致性快照和库存写事务，从 `FulJobStore` 解释租约重领之后旧 worker 为何写不进去。仓库权限从 `FulWarehouseAccess` 追到下载时的当前权限检查和导出范围。性能数字只按当时实验场景描述。

## 本轮补上哪些可执行证据

在原有 18 项恢复和监控检查后增加 7 项断言，经 [同一 CI 脚本](../../项目代码/tests/fulfillment_recovery_smoke.py)重复执行。三组数据由真实 API 建账，每组独立 SKU，H=6，请求数量均为 4。两个 HTTP 客户端用屏障一起发起请求，断言提交后的业务结果。用真实 MySQL、Redis、RabbitMQ，观察同一应用实例上每轮实际执行的一种顺序。

| 竞争场景 | 可接受的结果与验证点 |
| --- | --- |
| 两个不同订单预占 | 一单 `RESERVED`，另一单 `WAIT_STOCK`。H=6、R=4，单据持有量分别为 4/0，流水净占用为 4。取消赢家后 H=6、R=0，持有量和流水净值归零。 |
| 相同命令同时提交 | 两个结果完整一致。改变占用时长后复用该键，返回冲突码。数据库只有一条命令、一条预占事件，且 R、持有量及流水净值均为 4。 |
| 旧出库审批与履约预占 | 出库先提交时 H=2、R=0，履约待货；预占先提交时 H=6、R=4，旧单审批被拒且保持草稿状态。校验 ERP 流水条数、持有量和履约流水，覆盖失败事务是否留下副作用。 |

本轮是确定业务不变量的回归，吞吐和锁等待趋势引用原 M7 实验。双 JVM 历史竞态以及套件覆盖的其他 ERP 入口保留原证据。本轮没有新增生产容量、数据库主从切换、消息集群故障切换或线上经历的实证。

## 自测

遮住答案，用一张纸写下：初始 H=6、R=0；假设旧出库和预占都去掉 4，分别推演两种顺序。说清每一步谁持有行锁、事务失败时哪些写入一起回滚、重发请求的响应从哪里来。最后打开 Actions 成品里的 JSON，找到当次实际执行的顺序和对应数据库断言。
